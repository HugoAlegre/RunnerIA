Generar pruebas

        

          Arriba creás un módulo nuevo o una prueba dentro de uno existente.
          Abajo ves los módulos, podés agregar pruebas o renombrar un módulo (con confirmación).
          Son pruebas normales del Runner: si algún paso Gherkin todavía no está implementado en el proyecto, habrá que esperar a implementarlo para que la corrida pase en verde.
        


        

          Mini manual — cómo generar pruebas
          

            
Podés armar una prueba de dos formas. En ambos casos el resultado es un escenario Gherkin (.feature) que corre con SpecFlow + Playwright contra SOT.


            
1) Automático (recomendado si hay ticket)

            
    
              
  • Configurá una vez el email y API token de Jira en Configuración (no se muestran acá).
    • 
              
  • Pegá el Link Jira del ticket.
    • 
              
  • Opcional: adjuntá Documentación (.txt, .md, .docx, etc.).
    • 
              
  • Tocá Analizar: lee descripción, adjuntos de texto y comentarios funcionales; sugiere el módulo y arma escenarios.
    • 
              
  • Al ejecutar: captura por cada paso + informe Extent (como la suite SOT). Revisá y Guardá.
    • 
            


            
2) Manual

            
    
              
  • Elegí o creá el módulo, escribí el nombre del feature y el detalle.
    • 
              
  • Describí en claro qué se prueba (pasos, datos, resultado esperado).
    • 
              
  • Analizar → revisar Gherkin → Guardar.
    • 
            


            
Orden de los campos

            
    
              
  • Módulo = carpeta (ej. Alta de caja).
    • 
              
  • Nombre del feature = cómo se llama la prueba en la lista.
    • 
              
  • Detalle = qué se quiere lograr.
    • 
            


            
Tecnología que usa esta pantalla

            
    
              
  • Jira REST API — lee el ticket con el link (credenciales en Configuración).
    • 
              
  • Memoria al guardar — cada prueba confirmada queda como ejemplo para el próximo Analizar.
    • 
              
  • LLM opcional — en Configuración; pulí el borrador con contexto del proyecto (API OpenAI-compatible).
    • 
              
  • Gherkin / SpecFlow — formato del escenario (.feature).
    • 
              
  • Playwright — ejecuta la prueba en el navegador contra SOT.
    • 
              
  • Runner Operador (API local) — analiza, guarda y dispara la corrida.
    •

        Ayuda del runner
        
        
        
          
        
            
        1. Iniciar el servidor
        
            
        Doble clic en RunnerOperador\Iniciar-Runner.bat. No cierres la ventana negra mientras usás el runner.
        
          
        
          
        
            
        2. Elegir y ejecutar
        
            
        En Runner: elegí un módulo, después la prueba, revisá prerequisitos y tocá Ejecutar (pide confirmación). Al terminar se descarga un ZIP Titulo_yyyy-MM-dd_HH-mm-ss.zip con el informe. Si salís de Runner y volvés, se muestra la última corrida hasta que ejecutes otra.
        
          
        
          
        
            
        3. Generar pruebas
        
            
        En Generar pruebas podés armar casos manual (texto en claro) o automático (link Jira + documentación). Las credenciales de Jira van en Configuración.
        
          
        
          
        
            
        4. Configurar
        
            
        En Configuración: Ambiente SOT (DEV/QA), acceso SOT, SQL, COBIS y email/token de Jira (solo en este navegador). Las contraseñas SOT van en el archivo de secretos.
        
          
        
          
        
            
        5. LLM opcional (mejorar borrador)
        
            
        En Configuración → LLM opcional: activá el checkbox, pegá la API key (OpenAI u otro compatible), modelo (ej. gpt-4o-mini) y Base URL si no es OpenAI. La key queda solo en el navegador y se usa al Analizar.
        
          
        
          
        
            
        6. Ambiente QA + Auth OpenID
        
            
        Si elegís QA, se habilita la URL
              https://auth.accusys-qa.io/realms/uniweb-cloud/.well-known/openid-configuration.
              Abrila, aceptá el aviso de seguridad si aparece, y marcá Permitir acceso Auth QA para poder ejecutar.
        
          
        
        
        

        
        
          Cómo conectar el LLM opcional
          
        
            
          
              
        1. Andá a Configuración → sección LLM opcional.
          2. 
              
        2. Marcá Usar LLM al analizar.
          3. 
              
        3. Completá API key (no se guarda en el servidor; solo en este navegador si “Recordar” está activo).
          4. 
              
        4. Modelo: por defecto gpt-4o-mini (u otro que soporte tu proveedor).
          5. 
              
        5. Base URL: vacío = OpenAI (https://api.openai.com/v1). Para Azure/otros, la URL compatible con /chat/completions.
          6. 
              
        6. En Generar pruebas, al tocar Analizar, el borrador se pulí con el LLM + steps del proyecto + ejemplos guardados.
          7. 
              
        7. Si falla la API, el Runner sigue con el borrador local (no bloquea).
          8. 
            
        
          
        
        
        

        
        
          Cómo preparar ambiente QA (Auth OpenID)
          
        
            
          
              
        1. Configuración → Ambiente SOT → elegí QA.
          2. 
              
        2. Se muestra el bloque Auth OpenID con la URL .well-known/openid-configuration.
          3. 
              
        3. Tocá Abrir URL Auth QA (puede avisar seguridad: continuar/permitir).
          4. 
              
        4. Marcá Permito el acceso a Auth QA… y Guardar configuración.
          5. 
              
        5. Ejecutá la prueba: el login SOT QA usa ese flujo de autenticación.
          6.
