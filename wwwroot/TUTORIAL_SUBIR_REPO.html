1. Antes de empezar

Necesitás:

  • Git instalado (git --version en una terminal).
  • La URL del repositorio destino (HTTPS o SSH) que te den.
  • Credenciales: PAT / usuario+contraseña / clave SSH, según el proveedor.
  • Carpeta del proyecto, por ejemplo: C:\Repositorio\Proyecto\AutomatizacionSOT
Importante: el archivo Iniciar-Runner.bat es para desarrollo local. En un entorno online el servicio se arranca distinto; igual el bat sí puede ir al repo para que el equipo lo use en sus PCs.

2. Qué subir y qué no

Subir (sí) No subir (nunca)
Código del Runner (RunnerOperador/), tests SpecFlow, scripts run-*.ps1, MANUAL.md, Catalogo/repos-celula.json, Catalogo/proyectos-runner.json, appsettings.json (sin contraseñas reales) appsettings.secrets.json, .env, Catalogo/cache/, catalogo-sot.json generado, audit-runner.log, bin/ obj/, reportes Extent, node_modules/ (si aparece)

El archivo .gitignore del proyecto ya excluye la mayoría de lo sensible. Revisalo antes del primer push.

3. Secretos — no van al repo

Regla de oro: nunca hagas git add appsettings.secrets.json. Ahí están PIN del Runner, SQL, COBIS, PAT TFS, etc.

En tu PC (desarrollo)

  1. Versioná AutomatizacionSOT/appsettings.secrets.json solo como plantilla vacía.
  2. Los valores reales quedan solo en disco local y no se agregan a logs, ZIP, informes ni commits.

Plantilla de ejemplo (sí se puede versionar)

{
  "RunnerAuth": { "Pin": "" },
  "Aplicacion": { "Contrasena": "" },
  "Supervision": { "Password": "" },
  "SqlSot": { "Contrasena": "" },
  "Cobis": { "Contrasena": "" },
  "CatalogoTfs": { "Usuario": "", "Pat": "" },
  "Allowlist": {
    "JiraHosts": "atlassian.net",
    "GitHosts": "tfs2018,dev.azure.com"
  }
}

En el servidor (cuando esté online)

  1. Después del deploy, creá el secrets en el servidor (copiar/pegar o vault).
  2. No lo bajes del servidor al repo ni lo compartas por chat/correo.

4. Conectar el remoto que te den

Abrí PowerShell o Git Bash en la raíz del proyecto:

cd C:\Repositorio\Proyecto\AutomatizacionSOT
git status

Caso A — Ya es un repo Git local

Solo agregás (o cambiás) el remoto:

# Ver remotos actuales
git remote -v

# Si no hay origin, agregalo (reemplazá la URL por la que te den)
git remote add origin https://ejemplo.com/org/AutomatizacionSOT.git

# Si ya existe origin y te dan otra URL
git remote set-url origin https://ejemplo.com/org/AutomatizacionSOT.git

Caso B — La carpeta aún no es Git

cd C:\Repositorio\Proyecto\AutomatizacionSOT
git init
git branch -M main
git remote add origin https://ejemplo.com/org/AutomatizacionSOT.git

URLs típicas según proveedor

ProveedorEjemplo de URL
Azure DevOps / TFS Git http://tfs2018:8080/tfs/Coleccion/Proyecto/_git/NombreRepo
GitHub https://github.com/org/AutomatizacionSOT.git
GitLab https://gitlab.com/org/AutomatizacionSOT.git
Autenticación: en TFS/Azure suele usarse un PAT (o Credential Manager). En GitHub/GitLab: PAT o SSH. No guardes el PAT dentro del código.

5. Primer push (subida inicial)

  1. Confirmá que no hay secrets staged:
git status
# Si aparece appsettings.secrets.json → NO lo agregues.
# Si ya estaba trackeado por error:
git rm --cached AutomatizacionSOT/appsettings.secrets.json
  1. Agregá el proyecto y creá el commit:
git add .
git status
git commit -m "feat(runner): publicar AutomatizacionSOT y Runner Operador"

Si el equipo usa conventional commits en español, adaptá el mensaje.

  1. Subí al remoto:
# Primera vez (rama main o master según el remoto)
git push -u origin HEAD

# Si el remoto usa develop como rama principal:
git checkout -b develop
git push -u origin develop
Si el push pide usuario/contraseña, usá el usuario del proveedor y el PAT (no la contraseña de Windows, salvo que así lo indiquen).

6. Subir cambios después (día a día)

Cada vez que te pidan una mejora o corrección:

cd C:\Repositorio\Proyecto\AutomatizacionSOT
git pull
git status
git add .
git commit -m "fix(generar): descripción corta del cambio"
git push
Flujo recomendado: trabajá en una rama (feature/... o fix/...), hacé push y abrí Pull Request / Merge Request si el equipo lo exige. 
git checkout -b feature/mi-cambio
# ... editás código ...
git add .
git commit -m "feat(runneria): ajuste solapa proyecto"
git push -u origin feature/mi-cambio

7. En el servidor online (después del deploy)

  1. El pipeline o un admin hace git pull / publish del build.
  2. Se crea appsettings.secrets.json solo en el servidor.
  3. Se configura el servicio (IIS, Windows Service, Docker, etc.) — sin depender del bat para usuarios finales.
  4. Se prueban: login PIN, Generar → Analizar, sync de catálogo (si aplica).
Pieza¿En el repo?¿En el servidor?
Código + bat de desarrollo Sí Sí (código); el bat es opcional
appsettings.secrets.json No Sí (creado a mano / vault)
Cache / índice catálogo No Se genera al sincronizar

8. Checklist final

  • `.gitignore` incluye secrets, cache, bin/obj, reportes.
  • git status no muestra appsettings.secrets.json.
  • Remoto origin apunta a la URL que te dieron.
  • Primer commit + git push OK.
  • Documentaste al equipo: “secrets solo en servidor / máquina local”.
  • Si hay demo online: PIN y allowlist configurados fuera de Git.

Comandos de verificación rápida

git remote -v
git status
git check-ignore -v AutomatizacionSOT/appsettings.secrets.json
